## Question and alternatives

The question is whether a default can reduce initial selection work without hiding
wanted objects, or whether a neutral overview followed by explicit task scope is
more defensible. The editable-deck counterexample remains a regression constraint,
not a naming pattern to patch. No global file-type blacklist defines usefulness.

All policy arms use `Organization.search`, existing human-corrected `Work` identity
and native evidence. They compare:

1. The current shared ordering and first page.
2. A small diverse sample across existing project, collection or native reply
   contexts, with an explicit remainder. These contexts are selection buckets,
   not inferred logical identities or authority ranks.
3. Task-conditioned selection using explicit additional terms or existing scope
   and byte-bound review facts. With intent absent, return a neutral overview and
   preserve uncertainty instead of choosing a hidden task.

Every ranking arm receives the same information. An additional task clarification
or chosen scope counts as an extra interaction; it is not free oracle knowledge.
The competent direct-query comparator receives the same terms and scope. Review
conditions refer to the matched captured bytes, not approval of a work's present
unread bytes. All raw base-query candidates remain inspectable; eligibility changes,
deferral, presentation sampling and existing human joins are reported separately.

## Task protocol and metrics

Independent labels cover underspecified intent, several useful complementary
objects, many representations of one explicitly joined work, useful intermediates,
and distracting context diversity. For a declared task, report relevant objects
and unwanted objects in the first layer, wanted-object recall and rank, candidate
reachability, representation choice, repeated-work burden and expansions. A named
task can make a script or intermediate document the wanted result.

For an underspecified task with several plausible purposes, do not invent one
ground-truth precision score. Report plausible-context coverage, unsupported
authority claims and the information/selection needed to resolve the ambiguity.
Multiple useful objects must not be scored as noise merely because one is first.
A collapsed group is not a useful object unless the task actually asks for that
group. Representation choice inside an existing human-joined work has its own cost.

Directory comparators operate only inside the fixture's authorized project root
and document whether that folder/name is known. They use real bounded enumeration
and declared name/path filtering, not a deliberately noisy root listing. Direct
queries execute the existing shared core with the explicit task terms. These are
controlled task comparators, not Finder UI execution or a claim of Finder superiority.
Report unavailable/stale indexed evidence separately from a genuine negative query.

## Durable corrections and reconstruction

Use the real correction/review APIs for same-work joins, personal project filing,
collection membership/name and byte-bound review state. Compare selection before
correction, after correction, after a complete log reread and after reconstruction.
Current core has no public destructive full-index-rebuild command. A synthetic-only
derived-table reconstruction fixture is explicitly labelled as such: it removes
only derived log/session/delivery projections and run status while preserving
spans, file observations, captures, folder-membership observations, durable user
state and library namespace. Stored observations are historical evidence and must
not be misclassified as an expendable search projection. This experiment is
not deletion of the library and not a proposed product reset API.

No source content is executed. Fixture writes and test-only database reconstruction
stay inside disposable synthetic homes. Normal tests do not overwrite checked-in
evaluation records. Measured hypotheses and preference-dependent decisions are
separated in the final convergence ledger; Opus owns product and visual choices.
